# Отчет: разбор `evidence-based-learning-coach`

## 1. Назначение

`evidence-based-learning-coach` - это учебный управляющий промпт. Его задача не просто объяснить тему, а построить процесс обучения так, чтобы знание закреплялось через вспоминание, практику, ошибки, обратную связь и повторение.

Главный принцип:

> Тема считается изученной не тогда, когда материал прочитан, а когда его можно вспомнить, объяснить, применить, отладить и перенести в новый сценарий.

Для backend-направления это особенно важно: Kotlin, Ktor, Postgres, RabbitMQ, Docker, observability и архитектура плохо закрепляются пассивным чтением или просмотром уроков.

## 2. Общая структура промпта

| Блок | Назначение |

| Базовые правила | Фиксирует обязательные методы обучения |
| Рабочий процесс | Дает алгоритм изучения новой темы |
| Выбор техники | Подбирает метод под конкретную учебную проблему |
| Шаблон сессии | Описывает структуру одной учебной сессии |
| Типы вопросов | Задает формат вопросов для проверки понимания |
| Anki-правила | Защищает карточки от перегруза и бесполезной зубрежки |
| Практика | Переводит понимание в навык |
| Обратная связь | Определяет, как проверить правильность ответа или решения |

## 3. Философия обучения

Промпт опирается на идею durable understanding - долговременного понимания. Приоритет отдается не тому, чтобы "понять объяснение", а тому, чтобы самостоятельно восстановить и применить знание.

Слабые учебные действия:

- смотреть урок без последующей проверки;
- читать конспект и узнавать знакомые слова;
- копировать готовый код;
- просить готовое решение;
- делать огромные заметки без практики;
- создавать Anki-карточки до понимания темы.

Сильные учебные действия:

- объяснить тему без подсказки;
- решить задачу самостоятельно;
- найти ошибку в рассуждении или коде;
- сравнить похожие концепции;
- объяснить production-риск;
- повторить тему через несколько дней.

## 4. Базовые правила

### 4.1. Учить для воспроизведения и применения

Скилл требует учить не для recognition (узнавания), а для recall and application (воспроизведения и применения).

Плохой критерий:

```text
Я понял объяснение про транзакции.
```

Хороший критерий:

```text
Я могу объяснить commit/rollback, написать код с транзакцией, разобрать deadlock и объяснить, когда нужен retry.
```

### 4.2. Малые учебные циклы

Промпт предпочитает короткие циклы вместо длинных пассивных сессий.

Один цикл:

```text
короткая теория -> пример -> попытка без подсказки -> ошибка -> исправление -> повторение
```

Это лучше, чем три часа смотреть курс без практики.

### 4.3. Обязательное вспоминание

В каждой теме пользователь должен что-то достать из памяти:

- объяснить;
- выбрать подход;
- написать код;
- восстановить алгоритм;
- найти ошибку;
- ответить на уточнение.

Если вспоминания нет, обучение остается пассивным.

### 4.4. Интервальное повторение

Базовый график:

| Когда | Что делать |
|---|---|
| В тот же день | 5-10 вопросов на вспоминание |
| День 1 | Объяснить или собрать пример по памяти |
| День 3 | Смешанные вопросы и маленькая задача |
| День 7 | Debugging или перенос в новый сценарий |
| День 14 | Мини-проект или сценарий собеседования |

Повторение должно быть активным: не перечитать, а восстановить, объяснить, написать или отладить.

## 5. Рабочий процесс изучения темы

### 5.1. Target outcome - целевой результат

Первый шаг - сформулировать, что пользователь должен уметь после темы.

Плохо:

```text
Изучить RabbitMQ.
```

Хорошо:

```text
Написать producer и consumer, настроить manual ack, обработать retry и объяснить риск дублей.
```

Цель должна быть наблюдаемой. Ее можно проверить кодом, тестами, логами, метриками, состоянием БД или ответами на собеседовании.

### 5.2. Prerequisite check - проверка предпосылок

Перед темой нужно проверить фундамент.

Пример для RabbitMQ:

- HTTP vs asynchronous messaging;
- serialization;
- Docker Compose;
- обработка ошибок;
- idempotency;
- базовое понимание consumer/producer.

Если предпосылки слабые, скилл должен построить короткий bridge plan - план моста перед основной темой.

### 5.3. Learning map - карта темы

Тема делится на 4-8 блоков: от ментальной модели к production-рискам.

Пример для Postgres transactions:

1. Зачем нужны транзакции.
2. Commit и rollback.
3. Isolation levels.
4. Deadlocks.
5. Retry и idempotency.
6. Наблюдаемость.
7. Тестирование.

Для backend-тем обязательно добавляются reliability, observability, testing и production failure modes.

### 5.4. Practice loop - цикл практики

Каждый блок проходит одинаковый цикл:

```text
короткая теория
-> разобранный пример
-> повторить без подсказки
-> изменить пример
-> сломать пример
-> объяснить поломку
-> создать вопросы/Anki
-> запланировать повторение
```

Это главный механизм, который превращает материал в навык.

### 5.5. Interleaved practice - смешанная практика

После первого знакомства темы нельзя держать изолированно. Нужно смешивать похожие концепции.

Примеры:

- retry vs idempotency;
- logs vs metrics vs traces;
- API Gateway vs reverse proxy;
- transaction isolation vs locking;
- queue vs stream;
- unit test vs integration test.

Смысл interleaving: научиться отличать похожие вещи в реальных задачах.

### 5.6. Final transfer task - финальный перенос

В конце темы нужна задача, похожая на реальную backend-ситуацию.

Пример:

```text
Добавь в Ktor-сервис публикацию события booking.created через RabbitMQ.
Consumer должен обрабатывать событие, писать результат в Postgres и не создавать дубли при повторной доставке.
```

Acceptance criteria:

- сообщение публикуется;
- consumer подтверждает сообщение только после успешной обработки;
- повторная доставка не создает дубль;
- ошибка уходит в лог;
- есть тест или ручной сценарий проверки.

## 6. Выбор техники под ситуацию

| Ситуация | Что использовать | Чего избегать |
|---|---|---|
| Тема новая | Разобранные примеры, guided practice | Большой проект с нуля |
| "Понимаю, но забываю" | Active recall, Anki, spaced repetition | Перечитывание заметок |
| Путаются похожие темы | Interleaving, contrast cards | Изучение тем в изоляции |
| Курсы смотрятся, код не пишется | Reproduction without hints, маленькие задачи | Еще больше видео |
| Ошибка повторяется | Error-based learning, debugging prompts | Только правильные примеры |
| Нет уверенности в применении | Mini-projects, feedback, рост сложности | Одни определения |
| Подготовка к интервью | Contrast questions, production-risk cards | Trivia lists |

Этот блок полезен как диагностическая таблица. Он отвечает не на вопрос "что учить", а на вопрос "почему текущий способ обучения не работает".

## 8. Типы хороших вопросов

Скилл предпочитает вопросы, которые требуют активного ответа:

- чем X отличается от Y;
- когда использовать X;
- что сломается, если;
- найди ошибку;
- почему это опасно в production;
- как проверить, что это работает;
- что произойдет при отказе;
- напиши минимальный пример без подсказки;
- восстанови алгоритм по памяти;
- выбери подход и обоснуй.

Слабые вопросы:

- "Понял?";
- "Правда ли, что X полезен?";
- "Что из списка относится к X?";
- "Узнай термин по определению".

Для backend-собеседований сильнее всего работают вопросы про различия, отказ, последствия и проверку.

## 9. Anki-блок

Anki в этом скилле используется не для складирования лекций, а для удержания ключевых идей.

Плохая карточка:

```text
Расскажи про RabbitMQ.
```

Хорошая карточка:

```text
Front:
Что сломается, если consumer подтверждает сообщение до завершения бизнес-операции?

Back:
При падении после ack сообщение уже потеряно для брокера, а бизнес-операция может остаться незавершенной.

Дополнительно:
Ack лучше делать после успешной обработки или проектировать операцию идемпотентной.
```

Правила карточек:

- одна карточка - одна идея;
- ответ короткий;
- сначала прямой ответ;
- нюанс отдельно в `Дополнительно`;
- больше карточек на различия, ошибки и production-риски;
- не делать карточки до понимания темы;
- если карточка тяжелая, сначала подозревать плохую формулировку.

По твоим правилам из `AGENTS.md` перед добавлением карточек нужно проверять похожие материалы в Obsidian и Anki.

## 10. Практика по слоям

Скилл задает лестницу практики:

| Слой | Что проверяет |
|---|---|
| Recognition | Узнаешь ли концепт в готовом примере |
| Reproduction | Можешь ли восстановить без подсказки |
| Modification | Можешь ли изменить под новое требование |
| Debugging | Можешь ли найти и объяснить ошибку |
| Transfer | Можешь ли применить в новом сценарии |
| Production reasoning | Понимаешь ли отказы, retry, timeout, consistency, security, observability |

Эта лестница защищает от ложного ощущения знания. Если человек может только узнать правильный ответ, но не может изменить или отладить пример, тема еще не закреплена.

## 11. Обратная связь

Каждая задача должна иметь механизм проверки.

Для backend это может быть:

- unit test;
- integration test;
- ожидаемый HTTP response;
- строки в Postgres;
- количество сообщений в RabbitMQ;
- логи;
- Prometheus-метрики;
- Grafana dashboard;
- сравнение с официальной документацией;
- code review checklist.

Без feedback loop задача слабая: пользователь может думать, что сделал правильно, но не иметь доказательства.

## 12. Работа с источниками

Скилл требует проверять актуальные утверждения по первичным источникам, если они зависят от версий, tooling behavior, security guidance или production best practices.

Для твоего стека это значит:

- Kotlin - официальная документация Kotlin;
- Ktor - официальная документация Ktor;
- Postgres - официальная документация PostgreSQL;
- Exposed - документация JetBrains Exposed;
- Docker Compose - Docker docs;
- RabbitMQ - RabbitMQ docs;
- Prometheus/Grafana - официальные docs;
- MongoDB/ClickHouse - официальные docs;
- security - актуальные стандарты и рекомендации.

Если проверить нельзя, нужна честная пометка:

```text
Нужно проверить.
```

## 13. Типичные ошибки, которые промпт предотвращает

Скилл специально блокирует эти паттерны:

- долго смотреть или читать без recall;
- делать слишком много мелких trivia-карточек;
- делать одну огромную карточку на всю тему;
- спрашивать "понял?";
- давать задачи без критерия проверки;
- учить механизм без реального применения;
- не смешивать похожие темы;
- путать знакомость с владением;
- считать заметки доказательством знания;
- игнорировать production-риски.

## 14. Итоговый учебный конвейер

Практический алгоритм применения:

```text
1. Назвать тему и черновую цель.
2. Пройти диагностику.
3. Получить карту темы.
4. Разобрать worked example.
5. Повторить пример без подсказки.
6. Изменить требование.
7. Разобрать сломанный сценарий.
8. Ответить на вопросы.
9. Записать ошибки в Obsidian.
10. Создать 1-3 сильные Anki-карточки.
11. Повторить через 1/3/7/14 дней.
12. Закрыть тему через mini-project или мок-собеседование.
```

## 15. Как использовать для Kotlin Backend

Пример стартового запроса:

```text
Я начинаю изучать RabbitMQ для Kotlin/Ktor backend.
Я пока знаю только базовую идею очередей.

Сначала задай мне 5 диагностических вопросов.
Потом составь:
- target outcome;
- prerequisite check;
- learning map на 4-6 блоков;
- practice loop для первого блока;
- failure scenario;
- вопросы для самопроверки;
- график повторения 1/3/7/14 дней.

Не решай задачи вместо меня. Сначала требуй мою попытку.
```

Такой запрос связывает скилл с твоей реальной целью: Junior+/Middle Kotlin Backend для ЦУП РТ / АИС МИДИО и MIDIO-inspired проекта.

## 16. Краткая оценка

Сильные стороны:

- хорошо защищает от пассивного обучения;
- заставляет делать практику;
- включает интервальное повторение;
- подходит для backend;
- совместим с Obsidian и Anki;
- требует production-мышления;
- помогает готовиться к интервью.

Ограничения:

- сам не знает текущий уровень пользователя;
- перед темой нужна диагностика;
- Anki-карточки требуют проверки дублей;
- version-sensitive факты нужно сверять с официальными источниками;
- без дисциплины повторений эффект сильно падает.

Вывод:

> `evidence-based-learning-coach` лучше использовать как каркас всей учебной системы. Он задает не содержание темы, а способ превращать тему в долговременный backend-навык.
