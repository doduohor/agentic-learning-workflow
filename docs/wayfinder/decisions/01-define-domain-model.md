# Запись решения (Decision Record): Define Domain Model

## Статус (Status)

Принято.

Scope correction 2026-08-24: это решение читается в универсальной рамке programming learning. Backend, Kotlin и связанные технологии являются примерами текущего Learning Profile, а не границей системы.

## Контекст (Context)

Учебная система будет использовать `Codex CLI` и мультиагентный режим (multi-agent workflows), чтобы изучать темы программирования через диагностику, управляемое обучение, практику, генерацию вопросов, кандидатов в Anki, интервальное повторение и консолидацию знаний.

Перед проектированием шаблонов, агентов, команд и интеграций нужна стабильная доменная модель (domain model). Без нее термины вроде тема, блок, сессия, знание, практика, вопрос, слабое место и карточка будут расползаться между файлами и агентами.

Канонический глоссарий хранится в [CONTEXT.md](../../../CONTEXT.md).

## Решение (Decision)

Используем структурированную доменную модель вокруг учебного проекта (Learning Project).

Базовая иерархия:

```text
Learning Project -> Subject -> Topic -> Block -> Session
```

Расшифровка:

- учебный проект (Learning Project) - верхний контекст подготовки;
- предметная область или технология (Subject) - крупная область внутри проекта, например язык программирования, база данных, протокол, архитектурный подход, инструмент или платформа;
- тема (Topic) - конкретная учебная цель внутри Subject;
- блок (Block) - логическая часть Topic;
- сессия (Session) - датированный проход работы по Topic или Block.

Рабочие учебные артефакты:

```text
Goal.md              -> Topic Goal
Knowledge.md         -> Topic Knowledge Base
Practice.md          -> Practice Journal
Questions.md         -> Question Queue
RepetitionLog.md     -> Repetition Log
Weaknesses.md        -> Weakness Register
Sources.md           -> Source Record
```

Жизненный цикл темы (Topic lifecycle) использует одно основное состояние темы (Topic State):

```text
intake -> diagnosing -> planned -> learning -> practicing -> reviewing -> completed
paused
```

Модель освоения блока (Block mastery model):

```text
recognition -> recall -> application -> transfer -> production-ready -> stable
```

`production-ready` остается уровнем для блоков, где важны реальные ограничения применения. Если тема не имеет таких ограничений, блок может переходить от `transfer` к `stable` без искусственного production-гейта.

Блок считается изученным (Learned Block), когда есть:

- попытка без подсказок (no-hint attempt);
- проверенная практика или другой проверяемый ответ;
- разбор поломки или ошибки (failure analysis);
- ответы на уточняющие вопросы;
- отсутствие блокирующего слабого места (blocker Weakness).

Тема считается завершенной (Completed Topic), когда:

- все обязательные блоки (required Blocks) стали стабильными (stable);
- блоки с реальными ограничениями применения достигли `production-ready`, если этот уровень применим к теме или Learning Profile;
- не осталось блокирующих слабых мест (blocker Weakness).

Для агентов принимаем модель единственного владельца состояния (single-writer state model):

- учебный координатор (Learning Orchestrator) владеет состоянием Topic и применяет изменения, которые меняют состояние;
- поддерживающие агенты анализируют, предлагают, проверяют или добавляют записи в строго ограниченных границах;
- агент практики (Practice Agent) может добавлять структурированные попытки практики (Practice Attempts) в `Practice.md`;
- агент вопросов и карточек (Question/Card Agent) предлагает вопросы (Questions) и кандидаты в карточки (Card Candidates);
- куратор знаний (Knowledge Curator Agent) предлагает, как превратить заметки сессии и практику в очищенное знание (Knowledge);
- создание карточек требует проверки дублей (Duplicate Check) в Obsidian и Anki.

Знания делятся на два слоя:

- рабочая база знаний (Working Knowledge Base) - артефакты темы и текущее учебное состояние в репозитории;
- долговременная база знаний (Long-Term Knowledge Base) - устойчивые знания в Obsidian после консолидации.

Утверждения, зависящие от версии, реального поведения применения, production-поведения, безопасности, протоколов или поведения инструментов, требуют проверки источника (Source Check). Непроверенное утверждение (Unverified Claim) должно иметь пометку `Нужно проверить`, пока оно не подтверждено.

## Обоснование (Rationale)

Модель разделяет структуру и активность:

- блок (Block) - логическая часть темы (Topic), а не учебная сессия;
- сессия (Session) - датированный проход работы, а не блок материала;
- знание (Knowledge) - очищенное понимание, а не сырой лог чата;
- попытка практики (Practice Attempt) - активная работа, которую можно проверить и прокомментировать;
- слабое место (Weakness) - типизированная учебная проблема, которая меняет следующий шаг;
- кандидат в карточку (Card Candidate) - еще не Anki-карточка, пока не пройдены понимание, оценка ценности и проверка дублей.

Это защищает систему от типичных провалов:

- `Knowledge.md` не превращается в дамп переписки;
- `Goal.md` не превращается в смешанный конспект;
- Anki не наполняется низкоценными или дублирующими карточками;
- подагенты (subagents) не редактируют одни и те же файлы параллельно;
- пассивное перечитывание не считается стабильным знанием;
- тема не закрывается до переноса знания в новый сценарий (transfer) и разбора реальных ограничений применения, если они важны для темы или Learning Profile.

Для связей между файлами нужны устойчивые идентификаторы и локальные ссылки:

- устойчивый slug (Stable Slug) для идентичности Topic;
- идентификатор блока (Block ID);
- идентификатор вопроса (Question ID);
- идентификатор слабого места (Weakness ID);
- идентификатор попытки практики (Practice Attempt ID);
- ссылка на сущность (Entity Reference), которая сочетает ID и Markdown-ссылку.

## Последствия (Consequences)

Будущие шаблоны и инструкции агентов должны использовать термины из `CONTEXT.md` и не вводить синонимы без явного решения.

Следующие проектные шаги не должны заново определять доменную модель. Они должны специализировать ее в:

- Markdown-шаблоны;
- роли агентов Codex (Codex agent roles);
- команды жизненного цикла (lifecycle commands);
- интеграцию с Obsidian и Anki;
- небольшой прототип рабочего пространства темы (Topic Workspace).

Реализацию не начинаем, пока следующие decision tickets не уточнят структуру файлов и поведение агентов.

## Вне области (Out Of Scope)

Это решение не определяет:

- точные Markdown-шаблоны для каждого артефакта;
- файлы `.codex/agents/*.toml`;
- названия команд или поведение slash-команд;
- механизм записи обратно в Obsidian;
- автоматизацию Anki;
- интеграцию с календарем или задачником;
- машинно-читаемую YAML/JSON-схему.
