# Запись решения: сценарии жизненного цикла темы

## Статус

Принято.

Scope correction 2026-08-24: сценарии жизненного цикла темы универсальны для programming learning. Backend и RabbitMQ ниже используются только как пример текущего Learning Profile.

## Контекст

Предыдущие решения закрепили доменную модель, шаблоны рабочих артефактов темы и роли Codex-агентов. Теперь нужно определить, как пользователь и координатор обучения проводят тему через состояния:

```text
intake -> diagnosing -> planned -> learning -> practicing -> reviewing -> completed
paused
```

Это решение описывает повторяемые сценарии жизненного цикла темы. Оно не реализует slash-команды, не создает `.codex/agents/*.toml` и не создает реальные рабочие файлы темы.

Текущий Learning Profile пользователя: Junior+/Middle Kotlin Backend для ЦУП РТ / АИС МИДИО, с упором на Kotlin, Ktor, Postgres/Exposed, Docker/Docker Compose, RabbitMQ, observability, reliability, security, CI/CD и связанные backend-темы. Этот профиль задает приоритеты текущего пользователя, но не ограничивает систему backend-областью.

## Решение

На первом проходе проектируем не реальные slash-команды, а человекочитаемые сценарии, которые позже можно превратить в команды. Каждый сценарий описывает:

- цель;
- когда его можно запускать;
- кто участвует;
- какие файлы читаются;
- какие файлы в будущей реализации меняются;
- какие доказательства нужны;
- какие переходы состояния разрешены.

Сценарии первой версии:

```text
start/intake
diagnose
plan
learn-block
practice
review
repeat
pause
resume
complete
```

Сценарий `consolidate-ready` пока не входит в обязательный набор. Готовность к будущей консолидации фиксируется внутри `complete`, но подробная интеграция с Obsidian и Anki остается отдельным решением.

## Общие правила сценариев

1. Все изменения состояния применяет только координатор обучения.
2. Поддерживающие роли возвращают предложение координатору или делают только разрешенные новые записи.
3. Переход состояния без доказательств запрещен, кроме `intake`, `pause` и `resume`.
4. Каждая значимая запись должна ссылаться хотя бы на ID блока и одно доказательство: практическую попытку, вопрос, слабое место, повторение или источник.
5. `Goal.md`, `Knowledge.md` и `Weaknesses.md` меняет только координатор обучения.
6. Утверждения о версиях, реальном поведении применения, production-поведении, безопасности, протоколах и поведении инструментов требуют проверки источников. Если проверка не сделана, используется пометка `Нужно проверить`.
7. Кандидаты в Anki-карточки не создаются из сырого материала. Нужны понимание, ценность, след доказательств и будущая проверка дублей.

## Сценарии

### `start/intake`

Цель: превратить сырой запрос пользователя в тему на входе.

Пример запроса из текущего Learning Profile:

```text
Хочу изучить retry и DLQ в RabbitMQ для backend-сервиса.
```

Координатор обучения:

- выделяет предмет;
- формулирует тему;
- задает устойчивый slug;
- предлагает будущий путь рабочей папки темы;
- формулирует черновую цель;
- перечисляет ожидаемые рабочие файлы;
- ставит состояние `intake`.

Читает:

- `CONTEXT.md`;
- `docs/wayfinder/00-map.md`;
- будущий индекс тем, когда он появится;
- Obsidian-контекст только если без него нельзя понять текущий учебный маршрут.

В будущей реализации меняет:

- `Goal.md` в новой рабочей папке темы.

Поддерживающие роли обычно не нужны. Если запрос слишком широкий, координатор может предложить родительскую тему и более узкую первую тему.

Проверка перед переходом дальше:

- тема достаточно конкретна;
- есть устойчивый slug;
- есть предполагаемый путь рабочей папки;
- реальные рабочие файлы не создаются внутри этого решения.

Разрешенный следующий переход: `intake -> diagnosing`.

### `diagnose`

Цель: понять стартовый уровень, предпосылки, начальные слабые места и форму маршрута.

Координатор обучения задает диагностические вопросы или просит выполнить короткое задание. Диагностическая роль может предложить набор вопросов, но не меняет файлы напрямую.

Читает:

- `Goal.md`;
- `Knowledge.md`, если уже есть черновые знания;
- `Practice.md`, если уже были попытки;
- `Questions.md`;
- `Weaknesses.md`;
- `Sources.md`;
- релевантный Obsidian-контекст при необходимости.

В будущей реализации меняет:

- `Goal.md`, если координатор уточняет предпосылки, цель и состояние;
- `Weaknesses.md`, если координатор открывает начальные слабые места;
- `Questions.md`, если координатор принимает диагностические вопросы.

Поддерживающие роли:

- диагностическая роль предлагает предпосылки, стартовые вопросы, начальные слабые места и первый вариант маршрута;
- роль проверки источников подключается только если диагностика опирается на чувствительные утверждения;
- роль вопросов и карточек может предложить диагностические вопросы, но не кандидаты в карточки из сырого ответа.

Достаточная диагностика перед `planned`:

- цель темы понятна;
- предпосылки проверены или явно отмечены как риск;
- начальные слабые места найдены или явно не найдены;
- есть 3-7 блоков;
- блоки разделены на обязательные и необязательные;
- выбран первый активный блок;
- есть хотя бы одно диагностическое доказательство.

Разрешенный следующий переход: `diagnosing -> planned`.

### `plan`

Цель: превратить диагностику в управляемый маршрут темы.

Координатор обучения заполняет цель темы, карту обучения, критерии завершения, сводку активных слабых мест и первый следующий шаг.

Читает:

- `Goal.md`;
- `Weaknesses.md`;
- `Questions.md`;
- `Practice.md`, если диагностика включала попытку;
- `Sources.md`, если есть проверяемые утверждения.

В будущей реализации меняет:

- `Goal.md`;
- `Weaknesses.md`, если нужно уточнить начальные слабые места;
- `Questions.md`, если нужно активировать первые вопросы.

Правило выбора первого активного блока:

Координатор выбирает ближайший обязательный блок, который сильнее всего разблокирует практику и закрывает главный риск темы. Блок должен иметь понятные предпосылки и давать быстрый проверяемый практический сценарий из текущего Learning Profile.

Проверка перед переходом дальше:

- есть активный блок;
- каждый обязательный блок имеет понятный смысл;
- критерии завершения не требуют того, что система пока не умеет фиксировать;
- открытая blocker-слабость не игнорируется, а становится частью маршрута.

Разрешенный следующий переход: `planned -> learning`.

### `learn-block`

Цель: провести один блок через основной учебный цикл.

Базовый цикл:

```text
теория -> пример -> пользователь меняет пример -> намеренная поломка
-> пользователь объясняет поломку -> обратная связь -> фиксация доказательств
-> решение о следующем шаге
```

Координатор обучения ведет цикл. Практическая роль может исполнять активную часть: пример, изменение примера, поломку и первичную обратную связь.

Читает:

- `Goal.md`;
- `Knowledge.md`;
- `Practice.md`;
- `Weaknesses.md`;
- `Questions.md`;
- `Sources.md`.

В будущей реализации меняет:

- `Goal.md`, если меняется состояние, активный блок, статус блока или уровень освоения;
- `Knowledge.md`, если появилось отобранное знание;
- `Practice.md`, если была практическая попытка;
- `Weaknesses.md`, если обнаружена учебная проблема;
- `Questions.md`, если появились проверочные вопросы;
- `Sources.md`, если нужны проверки источников.

Поддерживающие роли:

- куратор знаний предлагает фрагменты для `Knowledge.md`;
- практическая роль может добавить новую практическую попытку в `Practice.md`, если координатор дал явное задание;
- роль вопросов и карточек предлагает вопросы после цикла;
- роль проверки источников проверяет чувствительные утверждения.

Проверка перед движением дальше:

- пользователь дал объяснение без подсказки или зафиксировано, почему это пока не удалось;
- пример был не только прочитан, но изменен;
- была намеренная поломка или разбор реальной ошибки;
- пользователь объяснил причину поломки;
- обратная связь дала конкретный следующий шаг;
- все новые слабые места имеют доказательство.

Разрешенные следующие переходы:

- `learning -> practicing`, если нужно активное применение;
- `learning -> reviewing`, если блок уже имеет достаточную практику и нужен контроль устойчивости;
- `learning -> learning`, если нужно продолжить текущий или следующий блок;
- `learning -> paused`.

### `practice`

Цель: получить проверяемую практическую попытку.

Практика может быть кодом, SQL, Docker Compose, схемой, разбором логов, проектным решением, объяснением компромисса или интервью-ответом.

Читает:

- `Goal.md`;
- `Knowledge.md`;
- `Practice.md`;
- `Questions.md`;
- `Weaknesses.md`;
- `Sources.md`.

В будущей реализации меняет:

- `Practice.md`, если практическая роль добавляет новую попытку;
- `Weaknesses.md`, если координатор открывает или обновляет слабое место;
- `Knowledge.md`, если координатор переносит исправленное понимание;
- `Questions.md`, если появляются последующие вопросы;
- `Goal.md`, если меняется уровень освоения, статус блока или следующий шаг.

Поддерживающие роли:

- практическая роль ведет задание и может добавить новую попытку в `Practice.md`;
- куратор знаний предлагает, что перенести в `Knowledge.md`;
- роль вопросов и карточек предлагает последующие вопросы;
- роль проверки источников подключается при чувствительных утверждениях.

Проверка перед повышением уровня блока:

- попытка имеет ID;
- есть ссылка на блок;
- результат проверен как `passed`, `partial`, `failed` или `rework-needed`;
- обратная связь отделена от тела попытки;
- слабые места открыты только при наличии доказательства.

Разрешенные следующие переходы:

- `practicing -> reviewing`, если практика достаточна;
- `practicing -> learning`, если нужна починка понимания;
- `practicing -> practicing`, если нужна переработка;
- `practicing -> paused`.

### `review`

Цель: проверить устойчивость понимания и решить, можно ли двигать блок или тему дальше.

Проверка не равна перечитыванию. Она использует вопросы, объяснение без подсказки, перенос в новый сценарий, разбор ошибки и проверку слабых мест.

Читает:

- `Goal.md`;
- `Knowledge.md`;
- `Practice.md`;
- `Questions.md`;
- `Weaknesses.md`;
- `RepetitionLog.md`;
- `Sources.md`.

В будущей реализации меняет:

- `Goal.md`, если меняется уровень освоения, статус блока, активный блок или состояние темы;
- `Weaknesses.md`, если слабое место исправлено, переоткрыто или стало серьезнее;
- `Questions.md`, если вопросы отвечены, провалены, архивированы или стали кандидатами в карточки;
- `RepetitionLog.md`, если проверка оформлена как повторение.

Доказательства для уровней освоения:

| Уровень | Минимальное доказательство |
|---|---|
| `recall` | объяснение без подсказки |
| `application` | проверенная практическая попытка |
| `transfer` | перенос в новый практический сценарий из текущего Learning Profile |
| `production-ready` | рассуждение о важных рисках и ограничениях применения: качестве, безопасности, тестировании, наблюдаемости, надежности, эксплуатации, совместимости или производительности |
| `stable` | успешное активное повторение |

Проверка перед движением дальше:

- нет открытой blocker-слабости по закрываемому блоку;
- уровень освоения подтвержден доказательствами;
- провалы не спрятаны, а привязаны к слабым местам;
- следующий блок выбран явно, если тема продолжается.

Разрешенные следующие переходы:

- `reviewing -> learning`, если нужен новый блок или ремонт понимания;
- `reviewing -> practicing`, если нужен новый практический проход;
- `reviewing -> completed`, если критерии завершения темы выполнены;
- `reviewing -> paused`.

### `repeat`

Цель: запланировать или провести активное повторение.

Повторение должно требовать действия: вспомнить, объяснить, применить, отладить или перенести. Простое перечитывание не считается активным повторением.

Читает:

- `Goal.md`;
- `Questions.md`;
- `Practice.md`;
- `Weaknesses.md`;
- `RepetitionLog.md`.

В будущей реализации меняет:

- `RepetitionLog.md`, если роль повторения добавляет запланированное повторение или результат;
- `Weaknesses.md`, если координатор открывает или обновляет слабое место после провала;
- `Goal.md`, если результат повторения меняет уровень освоения, статус блока или маршрут;
- `Questions.md`, если нужен новый вопрос.

Когда планировать повторение:

- после достижения `application`;
- после исправления major/blocker-слабости;
- после блока с важными реальными ограничениями применения;
- перед `completed`.

Если повторение провалено:

- случайная мелкая ошибка может остаться обратной связью;
- пробел, ошибочная модель, хрупкий навык или слепая зона применения открывают или обновляют слабое место;
- major-слабость требует шага на исправление;
- blocker-слабость запрещает закрывать блок или тему;
- уровень освоения может быть снижен только координатором.

Разрешенные следующие переходы:

- `reviewing -> learning`;
- `reviewing -> practicing`;
- `reviewing -> completed`;
- любое незавершенное состояние -> `paused`.

### `pause`

Цель: остановить работу без потери текущего маршрута.

Читает:

- `Goal.md`;
- при необходимости остальные файлы темы, чтобы записать короткий следующий шаг.

В будущей реализации меняет:

- `Goal.md`.

Проверка:

- записано предыдущее рабочее состояние;
- записан следующий шаг для возврата;
- незавершенная попытка или вопрос не считается закрытым.

Разрешенный переход: любое незавершенное состояние -> `paused`.

### `resume`

Цель: вернуться к теме после паузы.

Читает:

- `Goal.md`;
- `Practice.md`;
- `Questions.md`;
- `Weaknesses.md`;
- `RepetitionLog.md`.

В будущей реализации меняет:

- `Goal.md`;
- `RepetitionLog.md`, если обнаружены пропущенные повторения.

Проверка:

- восстановлено предыдущее рабочее состояние или выбран безопасный ближайший шаг;
- пропущенные повторения не игнорируются;
- открытые blocker-слабости остаются видимыми.

Разрешенный переход: `paused -> diagnosing | planned | learning | practicing | reviewing`.

### `complete`

Цель: закрыть тему как завершенную.

Читает:

- все рабочие файлы темы.

В будущей реализации меняет:

- `Goal.md`;
- `Questions.md`, если нужно зафиксировать состояние вопросов;
- `RepetitionLog.md`, если нужно запланировать последующее повторение;
- `Knowledge.md`, если координатор отмечает знание, готовое к будущей консолидации.

Проверка перед `completed`:

- все обязательные блоки имеют уровень `stable`;
- блоки с важными реальными ограничениями применения имеют уровень `production-ready` или `stable`, если этот уровень применим;
- нет открытых blocker-слабостей;
- активные major-слабости либо исправлены, либо явно вынесены за пределы темы;
- есть доказательства практики, объяснения поломки и повторения;
- кандидаты в карточки не продвигаются автоматически;
- готовность к консолидации отмечена, но сама интеграция с Obsidian и Anki не выполняется.

Разрешенный переход: `reviewing -> completed`.

## Переходы состояния

Основной путь:

```text
intake -> diagnosing -> planned -> learning -> practicing -> reviewing -> completed
```

Разрешенные возвраты:

```text
reviewing -> learning
reviewing -> practicing
practicing -> learning
learning -> learning
practicing -> practicing
```

Пауза:

```text
intake | diagnosing | planned | learning | practicing | reviewing -> paused
paused -> diagnosing | planned | learning | practicing | reviewing
```

Запрещенные переходы:

- `intake -> completed`;
- `diagnosing -> completed`;
- `planned -> completed`;
- `learning -> completed`;
- любой переход в `completed` при открытой blocker-слабости;
- повышение уровня освоения без нужного доказательства;
- закрытие блока с важными реальными ограничениями применения без разбора этих ограничений.

## Когда появляются вопросы и кандидаты в карточки

Вопросы создаются:

- после диагностики;
- после учебного цикла блока;
- после практической попытки;
- после провала вопроса или повторения;
- перед закрытием блока, если не хватает доказательств.

Кандидат в карточку создается только если материал:

- уже понят;
- важен для текущего Learning Profile;
- достаточно атомарен;
- имеет ссылку на знание, практическую попытку, слабое место, источник или вопрос;
- не является сырым куском объяснения.

Проверка похожих знаний в Obsidian и похожих карточек в Anki остается отдельным решением. До него кандидат может быть только `candidate`, но не продвинутой карточкой.

## Где нужен источник

Проверка источников запускается до записи в `Knowledge.md` или перед созданием кандидата в карточку, если утверждение связано с:

- версией инструмента или библиотеки;
- реальным поведением применения или production-поведением;
- безопасностью;
- семантикой протокола;
- поведением инструментов;
- рекомендацией, которая может устареть.

Если проверка невозможна в текущей сессии, координатор оставляет `Нужно проверить` и не делает вид, что утверждение подтверждено.

## Как слабые места меняют маршрут

Ошибка меняет маршрут, если она показывает:

- пробел;
- ошибочную модель;
- хрупкий навык;
- слепую зону применения.

Правила маршрута:

- minor-слабость не блокирует движение, но может породить вопрос или повторение;
- major-слабость требует запланированного шага на исправление;
- blocker-слабость запрещает закрывать связанный блок и тему;
- повторный провал активного повторения может понизить уровень освоения блока;
- исправление слабого места требует повторной проверки и ссылки на доказательство.

## Обоснование

Сценарии делают жизненный цикл темы управляемым, но не превращают проектное решение в преждевременную реализацию. Такой уровень детализации достаточен, чтобы позже написать slash-команды или инструкции агентов, не нарушая уже принятую модель единственного автора состояния.

Разделение `learning`, `practicing` и `reviewing` защищает систему от ложного прогресса:

- объяснение без применения не считается практикой;
- практика без повторения не считается устойчивым знанием;
- повторение без активного извлечения не считается проверкой памяти;
- карточка без понимания и проверки дублей не считается готовой Anki-карточкой.

## Последствия

- Будущий prototype ticket должен проверить эти сценарии на одной реальной теме.
- Будущий ticket по Obsidian/Anki должен уточнить проверку дублей, продвижение карточек и консолидацию знания.
- Будущий ticket по `.codex/agents/*.toml` может превратить роли и сценарии в инструкции, но не должен менять права записи без отдельного решения.
- Финальная спецификация системы должна включить эти сценарии как основу командного интерфейса.

## Вне scope

Это решение не создает:

- реальные slash-команды;
- `.codex/agents/*.toml`;
- рабочие файлы темы;
- prototype Topic Workspace;
- Obsidian/Anki-интеграцию;
- автоматическое создание карточек;
- финальный `learning-system-spec.md`.

## Критерии завершения

Решение завершено, когда:

- сценарии первого прохода перечислены;
- для каждого сценария описаны цель, роли, чтение, будущие записи и проверки;
- переходы состояния разрешены и запрещены;
- модель единственного автора состояния сохранена;
- вопросы, кандидаты в карточки, повторения, слабые места и источники встроены в жизненный цикл;
- карта wayfinder обновлена;
- новые устойчивые термины добавлены в `CONTEXT.md`, если они нужны.
